# A 股财务 PIT 小样本下载与审计协议 v1

## 1. 状态与目的

本协议承接已经认可的
`research/specifications/a_share_earnings_quality_pit_minimum_data_spec_v1.md`。

它只回答：

```text
当前 Tushare 权限和数据口径，能否可靠支持全 A 正式财报的公告日 PIT 研究？
```

小样本审计不是因子实验。它不读取未来收益，不计算 IC，不训练模型，不回测，
也不因某家公司财务表现好坏而调整样本。

本文件只冻结执行方案，**尚不授权下载**。用户审查并明确同意后，才运行一次
小样本下载与审计；完成后停止，不自动扩展为全量数据。

## 2. 已完成的只读权限探测

2026-08-05 已用当前 Tushare Token 做过不落盘的小样本探测：

| 接口 | 结果 | 已确认字段/情况 |
|---|---|---|
| `income` | 可用 | `ann_date`、`f_ann_date`、`end_date`、`report_type`、收入、净利润、`update_flag` |
| `cashflow` | 可用 | 公告日期、报告期、经营现金流、`update_flag` |
| `fina_indicator` | 可用 | 公告日期、报告期、ROE、每股经营现金流等 |
| `stock_basic` | 可用 | 当前上市 5537 只、退市 339 只；退市记录行业字段大面积缺失 |
| `disclosure_date` | 可用但历史覆盖有限 | 不能替代正式财报自身的公告日期 |

当前权限下 `income`、`cashflow` 必须指定 `ts_code`，不能按单一报告期一次取得
全市场。因此后续收集器必须逐股票、可断点续传；不得假定全量下载是一条请求。

对一个 2015-2019 历史样本，核心字段无缺失，并返回同键的 `update_flag=0/1`
记录；但重复记录的公告日和核心金额未发生变化。这证明接口返回更新标志，
**不能证明它保存了每一次真实历史修订**，仍需公告真值核验。

## 3. 样本规模与选择方法

### 3.1 固定规模

小样本固定为 50 家公司：48 家按规则确定的覆盖样本，加 2 家仅用于人工核验
流程稳定性的公开参考公司。样本财务好坏、历史收益和 Alpha158 结果都不得参与
选择。

### 3.2 48 家覆盖样本

先读取执行日的 Tushare `stock_basic` 上市/退市证券元数据，只用于构造下载样本，
并保存该次响应快照。固定分层如下：

| 分层 | 数量 | 细分 |
|---|---:|---|
| 上交所当前上市非金融普通 A 股 | 16 | 上市日前于2010年6只、2010-2019年6只、2020年以后4只 |
| 深交所当前上市非金融普通 A 股 | 16 | 上市日前于2010年6只、2010-2019年6只、2020年以后4只 |
| 北交所当前上市非金融普通 A 股 | 8 | 上市日期较早4只、较晚4只 |
| 历史退市沪深普通 A 股 | 8 | 上交所4只、深交所4只；`delist_date >= 2015-01-01`，只用于检查退市样本数据血缘 |

当前上市样本固定使用 `list_status=L`，并按交易所字段及代码后缀识别沪、深、北；
`stock_basic` 返回的非股票记录、CDR 或无法确认证券类型的记录不得进入候选集，
须写入排除清单。行业字符串先去首尾空格并统一大小写；若包含以下任一固定关键词
则排除：`银行`、`证券`、`保险`、`多元金融`、`信托`、`期货`、`金融控股`。
不得在看到抽样结果后增加或删除关键词。行业缺失的当前上市证券进入缺失清单，
不参与非金融覆盖样本抽取。退市记录行业字段缺失时不得猜测；保留在数据血缘
审计中，但不用于验证非金融财务公式。

每个细分内使用固定种子
`a_share_earnings_quality_pit_pilot_v1` 与 `ts_code` 以 UTF-8 字符串
`seed + "|" + ts_code` 拼接后计算 SHA256，按十六进制摘要升序、`ts_code`
升序作第二排序键，取前 N 个。北交所“较早/较晚”先按 `list_date` 升序并以
`ts_code` 打破并列，各取候选集前一半和后一半，再在各半内按相同哈希规则取4只。
若接口返回顺序改变，只要证券元数据快照相同，样本仍应一致。

### 3.3 两家参考公司

固定加入 `600519.SH` 与 `000858.SZ`，用于确认下载、三表对齐和人工公告核验
步骤可重复。若它们已由哈希抽入覆盖样本，则顺延取该分层下一只，使公司总数
仍为 50。参考公司不参与覆盖率是否代表全市场的结论。

## 4. 下载时间和请求边界

每家公司分别请求：

```text
接口：income, cashflow, fina_indicator
公告日期范围：2015-01-01 至 2025-06-30（Tushare 接口无公告日期区间参数，
按 `ts_code` 请求可用历史后，在本地按 `f_ann_date` 优先、`ann_date` 回退过滤）
保留报告期：2014-12-31 至 2024-12-31
```

范围包含 2014 年报作为部分同比基线，也包含 2024 年报在 2025 年的正常披露。
由于公告范围从 2015 年开始，2014 年一季报、半年报和三季报不在本试点中；因此
本试点不声称能为 2015 年各季度事件形成完整同比值。若未来研究期需要从2015年
开始，必须在全量下载协议中把相应 2014 年公告纳入。这里仍只审计财务数据；
不得连接或查看 2025-2026 收益。

接口请求本身不带报告期范围参数；本地过滤后才写入原始试点文件，过滤前的超出
范围响应不落盘。预计主体请求约为 `50 × 3 = 150` 次，另加证券元数据和必要的失败重试。固定
串行或低并发执行，遵守接口限速；遇到权限/频率错误时记录并停止或退避，不能
通过更换 Token、拆字段或无界重试绕过限制。

## 5. 原始字段与保存规则

### 5.1 原始响应

每个接口保留服务端返回的完整字段，不只保留当前认为有用的列；下载请求参数、
响应列、行数、时间、状态和错误写入请求日志。至少必须存在：

- 身份：`ts_code`；
- 时点：`ann_date`、`f_ann_date`（接口有则必须保留）、`end_date`；
- 版本：`report_type`、`update_flag` 或其他服务端版本字段；
- 利润表：`total_revenue`、`n_income`；
- 现金流量表：`n_cashflow_act`；
- 财务指标：接口返回的公告/报告期身份字段及质量核验字段。

不得在原始层去重、填充公告日、修改单位、改列名或覆盖旧版本。

### 5.2 文件布局

全部试点文件只能写入：

```text
data/external/tushare/a_share_financial_pit_v1/pilot/raw/
data/external/tushare/a_share_financial_pit_v1/pilot/normalized/
data/external/tushare/a_share_financial_pit_v1/pilot/manifest.json
output/data_audits/a_share_financial_pit_v1/pilot/
```

建议聚合保存为 `income.csv.gz`、`cashflow.csv.gz`、`fina_indicator.csv.gz`，每行
增加 `requested_ts_code`、`request_started_at_utc` 和原始接口名。证券元数据、
固定样本清单、请求日志和字段结构分别保存，不能混进三张财务表。

所有写入使用临时文件 + 原子替换；断点只按“接口 + ts_code 已成功且文件哈希
通过”认定完成。结果不得写入 `mlruns`、`examples` 或 Qlib 行情目录。

## 6. 标准化与版本处理

原始下载结束后才生成标准化副本：

1. 日期解析失败的原值保留在异常表；
2. `available_date = f_ann_date`（合法时），否则取合法 `ann_date`；
3. `available_date` 不得早于 `end_date`，不得静默用报告期补公告日；
4. 同一版本只从自身 `available_date` 起可见；
5. 重复键不删除，先按全部返回字段判断是完全重复、更新标志重复，还是金额修订；
6. 三表分别标准化，不能因一张表缺失而从另一张表推断金额；
7. 金额单位保持原始单位，并在 manifest 中记录；禁止未经记录缩放至万元/亿元。

标准化过程必须可由原始层和代码完整重建。

## 7. 公告真值核验

从下载结果中固定选取恰好 24 个互不重复的“公司 + 报告期”做人工/半自动核验。
先构造候选键 `ts_code + "|" + end_date`，使用种子
`a_share_earnings_quality_pit_spot_check_v1` 按与公司抽样相同的 SHA256 规则排序，
并按以下顺序选取；已入选的键从后续组候选中排除：

- 存在重复、金额变化或更新标志的记录4个；不足部分由当前上市普通记录补齐；
- 退市公司记录4个；
- Q1、半年报、三季报、年报各4个，共16个；某类不足时记为审计覆盖缺口，不能
  用另一报告类型替代并仍宣称满足24个核验样本。

不能选择最容易或最整齐的记录。核验源优先为交易所或巨潮资讯公告页/原始公告，
至少检查：

1. 公司与报告期；
2. 首次正式公告日期；
3. 是否有更正/修订以及更正日期；
4. 营业收入、净利润、经营活动现金流净额；
5. 公告单位与 Tushare 金额单位是否一致。

单位统一后，关键金额允许误差为 `max(1 元, |公告金额| × 1e-6)`。金额匹配率以
官方公告和 Tushare 均存在的 `营业收入`、`净利润`、`经营活动现金流净额` 字段
逐字段计算；缺失字段单独计入覆盖率，不得从匹配率分母中静默删除。无法取得
官方公告的样本必须记录原因并另取同组下一条补足，但原样本仍保留在不可核验
清单中。

## 9. 预先冻结的通过条件

全部满足才判定 `pilot_pass`：

1. 50家公司样本清单可由保存的 `stock_basic` 快照和哈希规则复现；
2. 三个接口成功或明确无数据的请求覆盖 100%，无未解释失败；
3. 有财报记录的非金融样本中，`ann_date/f_ann_date` 至少一个合法的比例
   不低于 99%；不得存在被报告期静默填充的公告日；
4. 利润表与现金流量表按公司、报告期、可得版本的可解释对齐率不低于 95%；
5. 对应已上市期间，当前上市样本预期正式报告期的核心金额覆盖率不低于 95%；
6. 退市样本在退市前预期报告期的核心金额覆盖率不低于 75%，否则视为潜在
   幸存者数据缺口；
7. 24个官方核验样本中不得有未解释的公告日期错误；关键金额匹配率不低于 95%；
8. 所有重复/更新记录都在版本审计表中解释，没有静默覆盖；
9. 原始文件、请求日志、字段清单和 SHA256 完整，可从原始层重建标准化结果。

发生以下任一情况则为 `pilot_blocked`：接口权限不足、系统性公告日错误、官方
核验发现更正/修订但 Tushare 无法保留修订前后值及各自可得日期、退市数据严重
缺失、核心字段单位不明、任一预定报告类型无法补足核验样本，或官方核验无法
完成。

门槛失败后只能修复数据链或更换数据源，不能降低门槛后继续因子研究。

## 10. 执行结束点

用户批准后，一次执行小样本下载、标准化与审计。无论 `pilot_pass` 还是
`pilot_blocked`，都在报告生成后停止等待用户审查。

本协议不授权：全量全 A 财务下载、因子定义、收益标签读取、模型训练、回测，
或将财务数据混入 Alpha158/Core13。
