# 数据完整性缺陷：日历领先于行情 21 个交易日

| 项 | 值 |
|---|---|
| 脚本 | `scripts/migration/probe_store_tail_v1.py` / `_v2.py`、补丁 `scripts/data_collector/update_daily_market_data_v1.py` |
| 影响 | 实盘信号在最新交易日**静默产出全 NaN 清单** |
| 状态 | **已诊断、已修补、已补齐数据** |
| 日期 | 2026-09-13 |

## 1. 现象

生成实盘清单（asof = 2026-09-11）时：
- 30 只标的**目标股数全为 0**、价格全 NaN、仓位利用率 0.000；
- 毒尾否决**屏蔽 0 个候选**（正常应为约 3.8%）。

两个异常同时出现 → 指向同一原因。

## 2. 根因

**store 的日历末端与实际行情末端不一致**：

```text
calendars/day.txt 末端        : 2026-09-11   (2,843 天)
个股 bin 实际数据末端          : 2026-08-13   (5,540 只)
只有 1 个 instrument (指数) 到 2026-09-11
```

即**日历被扩展到了 2026-09-11，但这 21 个交易日的行情从未抓取**。
于是 `$close` 在 2026-08-14 ~ 2026-09-11 全为 NaN ——
价格查不到（股数归零），毒尾分也因滚动窗口全 NaN 而无法屏蔽任何候选。

**这个缺陷是静默的**：不报错，只是产出全 0 清单。

## 3. 为什么更新脚本没能修好它

`update_daily_market_data_v1.py` 第 290 行用**日历末日**当作"数据末端"：

```python
last_store_day = calendar[-1]              # = 2026-09-11
days = get_recent_trading_days(pro, end_date, last_store_day)
if not days: print("[skip] no new trading days after", last_store_day)
```

日历既然已经是 2026-09-11，就永远判定"无新交易日"，
**这 21 天的缺口永远不会被补上**。且 `raw/` 目录下按日文件也确实止于 2026-08-13。

## 4. 修补

把基准改为 `min(日历末日, raw 行情末日)`，并同时检查 `raw_dir` 与 `raw_dir/"raw"`
两种目录布局（实测按日文件在后者）：

```text
[warn] 日历末日 2026-09-11 领先于行情末日 2026-08-13 (29 天); 以行情为准补齐
[plan] 21 new trading days: 2026-08-14 .. 2026-09-11
```

## 5. 补齐结果

```text
[fetch] 21 days downloaded
[dump]  appended 21 days into ~/.qlib/qlib_data/cn_data_2026
[repair] rebuilt appended window for 5,563 stocks (suspended-day fix)
[verify] store calendar now ends 2026-09-11 (2843 days)
```

复核：**5,550 只个股数据现在到 2026-09-11**（此前为 5,540 只到 2026-08-13）。

## 6. 补齐后的实盘清单（asof = 2026-09-11）

| 项 | 值 |
|---|---|
| 标的数 | 30 |
| 实际投入 | **424,760 元** |
| 仓位利用率 | **0.850**（此前全 NaN 时为 0.000） |
| 否决屏蔽 | **130 / 3,360 = 3.9%**（与回测的 3.8% 一致 ✓） |
| 行业 cap3 | 生效 |
| 不可买 | 1 只（600742.SH 175.5 元 > 166.67 元上限） |

## 7. 教训与后续要求

1. **"不报错"不等于"正确"**：日历领先于数据会让实盘信号静默归零。
   后续任何生成实盘清单的脚本，**必须校验 asof 当日是否有非空价格**，
   否则视为失败退出（本次已由 NaN 现象暴露，但应改为显式断言）。
2. **数据更新应以"实际数据末端"为准，不是"日历末端"**。
3. 同类风险：任何依赖 `calendar[-1]` 作为"今天"的代码都应复核。
4. **仍未解决**：`load_amount_avg` 返回零列导致流动性过滤为 no-op（见
   `a_share_five_factor_500k_decision_v1.md` §2-3）——同属"静默失效"类缺陷。
