# 让监测真正推进：延伸快照缓存 + 修两个静默缺陷

| 项 | 值 |
|---|---|
| 触发 | 用户要求给每日更新配置自动调度；配置过程中发现"监测其实是复读" |
| 结果 | 监测/归因现在随新数据推进；**滚动 12 个月由 −10.42% 改善到 +0.67%** |
| 日期 | 2026-09-30 |

## 1. 缺陷一：生成器没有调仓网格（最严重）

`generate_five_factor_veto_holdings_v1.py` 原逻辑是 `asof = 最新 daily_basic 日期`，
随后直接以该日期生成信号——**与回测的 10 交易日网格毫无关系**。

两个后果：

| 后果 | 说明 |
|---|---|
| **每天跑 = 每天新信号** | `wsl_run_daily_update.sh` 里就含这一步；一旦设为每日调度，模拟盘会**每日调仓**，彻底偏离策略定义 |
| **实盘与网格错相位** | 回测网格是 `cal[::STEP]`；实测网格日为 **09-01 / 09-15**，而实盘信号落在 **09-11 / 09-29** |

**已修（网格对齐）**：

```text
eligible = calendar[calendar >= BT_START][::STEP]       # 与回测完全相同的相位
eligible = [d for d in eligible if d <= 最新数据日 and d 有 daily_basic]
target   = eligible[-1]                                  # 最近可支撑的网格日
asof     = target                                        # 用网格日, 不用最新数据日
若 上次信号 >= target -> 跳过(该网格日已生成)
```

补做错过的调仓时 `asof` 落在**已过去的网格日**上，只用到该日及之前的数据 → **不引入前瞻**。

## 2. 缺陷二：`daily_basic` 更新器以 store 日历为截止日

与之前修的行情更新器**同一类**（见 `data_integrity_calendar_ahead_of_data_v1.md`）：
store 日历是随行情 dump 一起推进的，所以它把日历末端当成"今天"。

实测：2026-09-30 运行时报 `[skip] no missing days`，但数据实际只到 09-11（**落后 9 个交易日**）。

**已修**：用 tushare 交易日历把候选日补到最新。修完立刻正确识别出缺失的 8 天。

> 这已是本项目第 8、9 个"静默失效"缺陷。**共同特征：不报错，但结果错。**

## 3. 缺陷三：监测在"复读"

`monitor_strategy_decay_v1.py` 与 `analyze_strategy_return_attribution_v1.py`
都读冻结快照 `snapshots_500k_10day.pkl`（止于 **2026-06-23**）。

→ **每月跑都报同一组数字**，看起来在监测，实际没有推进。

**已修**：新增 `scripts/rebuild_snapshots_to_date_v1.py`，生成**独立的**延伸缓存：

```text
snapshots_500k_10day.pkl            ← 冻结研究产物, 绝不覆盖
snapshots_500k_10day_extended.pkl   ← 延伸版, 随新数据推进
```

**为什么不覆盖冻结缓存**：所有已发布数字（交付总览、各决策记录）都基于它；
覆盖会让历史结果**静默改变且不可追溯**。

**安全断言**（避免延伸过程本身静默失效）：
- 每期候选数中位必须 > 500
- 延伸后期数不得少于冻结缓存

延伸结果：

```text
261 期, 2016-01-04 .. 2026-09-15   (冻结版 255 期, 止于 2026-06-23)
新增 6 期: 2026-07-07, 07-21, 08-04, 08-18, 09-01, 09-15
每期候选数 中位 3,023  最小 1,764  最大 3,573
```

## 4. 推进后的结果（**这是本次最有价值的产出**）

### 衰减监测

```text
              冻结版(至 2026-06-23)   延伸版(至 2026-09-15)
全期年化净超额      +16.99%              +17.44%
滚动12个月(当前)    −10.42%   ⚠          +0.67%   正常
滚动12个月为正比例   87.6%                86.4%
样本天数            2,546                 2,601
```

**滚动 12 个月由 −10.42% 转为 +0.67%，状态由"⚠ 转负"回到"正常"。**

### 收益归因

| | 冻结版 | **延伸版** |
|---|---|---|
| 全期 基础 alpha | +8.50pp | **+9.23pp** |
| 全期 否决 | +4.82pp | **+4.67pp** |
| 全期 价格过滤 | +2.59pp | **+2.44pp** |
| 全期 合计 | +16.99pp | **+17.44pp** |
| **最近 12 个月** 基础 | −22.02% | **−8.18%** |
| **最近 12 个月** 否决 | +18.41pp | **+15.96pp** |
| **最近 12 个月** 价格 | −3.19pp | −5.74pp |
| **最近 12 个月** 合计 | **−10.42%** | **+0.67%** |
| 否决为正的滚动窗口比例 | 66.0% | 66.8% |

**结构没有变，但程度显著缓和**：

- **基础价值 alpha 仍为负**（−8.18%，比之前的 −22.02% 好很多）
- **否决仍是承重墙**（+15.96pp）
- 结论不变：**近年超额来自风险剔除而非选股 alpha；否决失效 = 策略失效**

## 5. 自动化（Windows 计划任务）

| 任务 | 触发 | 动作 |
|---|---|---|
| `qlib-daily-update` | 周一至周五 18:00 | 数据更新 → 网格对齐生成信号 → 模拟盘 mark-to-market |
| `qlib-monthly-report` | 每 4 周 09:00 | [A] 前瞻轨迹 + [B] 承重墙检查 |

均实测 `LastTaskResult=0`。

**为什么用 Windows 计划任务**：WSL2 虚拟机空闲时自动关闭，VM 内的 cron/systemd timer
不会可靠触发；而 `wsl.exe` 被调用时会拉起发行版。

**已知限制**：任务只在用户登录时运行。
- `-LogonType Password` 需用户密码 → 我不代做
- `-LogonType S4U` **无网络访问** → 数据更新必然失败
- 以 SYSTEM 运行 → WSL 发行版按用户注册，找不到
- **实际缓解**：已启用 `StartWhenAvailable`，错过的运行会在下次登录后补跑

## 6. 结论边界

1. 延伸缓存只新增 6 期，**滚动 12 个月改善主要反映 2026-07~09 这三个月的行情**，
   样本仍短，不足以断言"衰减结束"。
2. 网格对齐是**从本次起**生效——实盘此前两次信号（09-11、09-29）与网格错相位，
   这段前瞻轨迹与回测不是严格同相位，应在评估时剔除或标注。
3. 延伸仍有静默失效风险（如网格相位算错），故保留了两条量级断言。
4. **时间维度样本外**仍未闭合。
